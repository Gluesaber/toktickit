# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Deliver a working Requester-facing ticketing experience: a Requester (selected through a temporary
Development Requester Selector) can create an IT support ticket with attachments, find it again in a
personal My Tickets list via search/filter/sort/pagination, open a read-only Ticket Detail screen, and
manage that ticket's attachments — all while one Requester is provably prevented from seeing another
Requester's tickets.

## 2. Stakeholder Request Interpretation

The IT department wants a self-service intake screen so a Requester can describe a problem (category,
related system, priority, description), attach evidence, and get back an official ticket number. Because
real login doesn't exist until Lab 3, we simulate "who is using the app" with a Development Requester
Selector: the student picks a seeded Requester first, and every subsequent screen behaves as if that
Requester is logged in — including strict ownership boundaries between Requesters. The stakeholder
also wants the visual and interaction language (forms, lists, badges, states) established now so it can be
reused without rework in later sprints.

## 3. Scope

### Included
- Development Requester Selection screen (testing mechanism, not authentication) and Change Requester.
- Create Ticket: form, validation, attachment selection, submission, success/failure states.
- My Tickets: Requester-owned, paginated, searchable, filterable, sortable ticket list.
- Requester Ticket Detail: read-only ticket fields, attachment list.
- Attachment lifecycle: add, download, soft-remove (with reason), on an owned ticket.
- Ownership protection across all Requester-scoped endpoints and screens.
- Zen Green visual system and reusable form/list/badge/state components.
- Reference data (Categories, Related Systems, active Requesters) seeded and served from PostgreSQL.

### Excluded
- Authentication, sessions, passwords, tokens, real role-based authorization.
- IT Staff dashboard/queue, claiming/reassigning tickets, IT Priority changes.
- Public Comments, Internal Notes, Actions Taken.
- Any ticket status beyond the initial `New` (no resolve/close/reopen/cancel).
- Administrator management of users, Requesters, roles, or reference data.
- Hard deletion of attachments; duplicate-submission idempotency keys (see §11).

## 4. Functional Requirements

- FR-01 Provide a Development Requester Selection screen listing active Requesters; selecting one and
  continuing enters the application in that Requester's context.
- FR-02 The application shell displays the current Requester's name and a Change Requester action on
  every Requester-scoped screen.
- FR-03 Provide a Create Ticket screen capturing Category, Related System, Requested Priority, Summary,
  Description, and Attachments, with system-generated fields (Ticket Number, Ticket Date, Requester)
  shown as read-only.
- FR-04 Validate the Create Ticket form on both frontend and backend, with field-level error messages.
- FR-05 On successful submission, create one Ticket, return the generated Ticket Number, and show a
  success confirmation with a next action.
- FR-06 Provide a My Tickets screen listing only the current Requester's tickets.
- FR-07 My Tickets supports free-text search across Ticket Number and Summary.
- FR-08 My Tickets supports filtering by Category, Related System, Requested Priority, and Current Status.
- FR-09 My Tickets supports sorting by Ticket Date, Ticket Number, Current Status, and Requested Priority.
- FR-10 My Tickets supports pagination with a page-size control and page navigation.
- FR-11 My Tickets shows distinct loading, empty, no-results, and failure states.
- FR-12 Provide a Ticket Detail screen showing all ticket fields read-only, for the owning Requester only.
- FR-13 Ticket Detail lists Attachments (active and removed) with metadata.
- FR-14 A Requester can add a new Attachment to an owned ticket from Ticket Detail.
- FR-15 A Requester can download an active Attachment they own.
- FR-16 A Requester can soft-remove an active Attachment they own, optionally with a reason.
- FR-17 Every Requester-scoped API call enforces ownership server-side and rejects cross-Requester access.
- FR-18 All Lab 2 screens reuse one consistent Zen Green visual system.
- FR-19 All Lab 2 screens work at desktop (≥992px), tablet (768–991px), and mobile (<768px) without
  horizontal scrolling or clipped content.
- FR-20 Reference data (Categories, Related Systems, active Requesters) loads from PostgreSQL via the API.

## 5. Business Rules

**Given (mandatory) examples, kept verbatim:**
- BR-01 The official Ticket Number is generated by the backend and must be unique.
- BR-02 A new Ticket begins with Current Status New.
- BR-03 Lab 2 uses a Development Requester selector instead of login. The selected identity is for testing
  only and is not authentication.

**Defaults and system-generated values**
- BR-04 Ticket Date is a system-generated UTC timestamp at creation time and is read-only.
- BR-05 Ticket Number uses the pattern `TK-<4-digit creation year>-<6-digit zero-padded ticket id>`
  (e.g. `TK-2026-000042`), generated only after the Ticket row is successfully inserted (see §11).
- BR-06 `requesterId`, `ticketNumber`, ticket date, and Current Status can never be supplied or overridden
  by the client in the create-ticket request body.

**Requester selection and switching**
- BR-07 Only Requesters with `isActive = true` appear in the Development Requester Selection dropdown.
- BR-08 The selected Requester's id is stored client-side as the current testing context and is sent
  explicitly with every Requester-scoped API call; the backend never infers identity another way.
- BR-09 Changing the Requester clears all currently displayed Requester-scoped data and reloads it for the
  newly selected Requester.
- BR-10 If no Requester is currently selected, any Requester-scoped screen redirects to the Selection screen.

**Ownership**
- BR-11 A Ticket is owned by exactly the Requester referenced by its `requesterId`; ownership never
  transfers within Lab 2.
- BR-12 The backend rejects (404, so as not to confirm existence) any request for a Ticket or Attachment
  whose owning ticket's `requesterId` does not match the requesting Requester.
- BR-13 My Tickets only ever returns tickets owned by the currently selected Requester.

**Search, filtering, sorting, pagination**
- BR-14 The ticket list is searchable by Ticket Number (partial match) and Summary (partial,
  case-insensitive match).
- BR-15 The ticket list is filterable by Category, Related System, Requested Priority, and Current Status.
- BR-16 The ticket list is sortable by Ticket Date (default: newest first), Ticket Number, Current Status,
  and Requested Priority; ties break by Ticket Date descending, then id descending.
- BR-17 Permitted page sizes are 10, 25, 50 (default 10). A page beyond the last page returns an empty
  result set with correct pagination metadata, not an error.
- BR-18 Unrecognized or invalid query parameters are handled per the exact rules in `api-spec.md`
  (ignored with a safe default, or rejected with 400) — never allowed to crash the request.

**Validation and duplicate-submission prevention**
- BR-19 Ticket Summary is required, trimmed, 5–120 characters after trimming.
- BR-20 Ticket Description is required, trimmed, 10–2000 characters after trimming.
- BR-21 Category, Related System, and Requested Priority are required and must reference an active,
  existing record or valid enum value.
- BR-22 The Submit button is disabled while a create-ticket request is in flight; the frontend never fires a
  second request while one is pending.
- BR-23 The backend does not implement idempotency keys in Lab 2 — an intentionally repeated submission
  with identical data creates a second, independent Ticket. Documented as a known limitation (§11),
  not a defect.

**Failure behavior and data retained after errors**
- BR-24 On validation failure, all previously entered field values remain in the form; only invalid fields
  show error messages.
- BR-25 If the backend or network is unavailable during submission, the form shows a safe generic failure
  message, retains all entered values, and allows retry without re-entering data.
- BR-26 If a Ticket is created but a selected Attachment fails to upload, the Ticket remains saved; the
  failure is reported per file, and the Requester may retry the attachment from Ticket Detail.

**Attachments**
- BR-27 Allowed Attachment types are JPG, JPEG, PNG, WEBP, and PDF, enforced by both extension and MIME type.
- BR-28 Maximum Attachment size is 5 MB per file; oversized files are rejected client-side before upload
  and re-validated server-side.
- BR-29 A Ticket may have at most 5 active (non-removed) Attachments at a time; a 6th active Attachment
  is rejected.
- BR-30 Attachments are stored under a generated safe filename (not the client-supplied name), to avoid
  path traversal and collisions; the original filename is kept as display metadata.
- BR-31 Removing an Attachment is always a soft removal: the row is kept, marked with a `removedAt`
  timestamp and optional reason, and never physically deleted during Lab 2.
- BR-32 A removed Attachment stays visible in Ticket Detail as metadata (filename, size, upload date,
  removed date, reason) but its download/preview action is disabled in the UI and rejected by the API.
- BR-33 Only the Requester who owns an Attachment's ticket may add or remove that ticket's Attachments.
- BR-34 If an Attachment upload fails for any reason (network interruption, type/size rejection, or the
  5-active-Attachment limit), the existing Attachment list is left unchanged, a per-file error message is
  shown, and any other files in the same batch may still succeed independently.

**Inactive Requesters**
- BR-35 An inactive Requester (`isActive = false`) never appears in the Development Requester Selection
  dropdown.
- BR-36 Tickets created by a Requester before deactivation remain in the database and queryable by the
  original API, but that Requester can no longer be selected as the active testing context (Lab 2 has no
  admin UI to toggle `isActive`; this rule is asserted against seed data only).

**Empty and no-results states**
- BR-37 If the Requester has zero Tickets, My Tickets shows an "empty" state distinct from a "no
  results" state.
- BR-38 If the Requester has Tickets but the current search/filter combination matches none, My Tickets
  shows a "no results" state with a clear-filters action.
- BR-39 If no active Development Requesters exist, the Selection screen shows an empty state and does not
  allow proceeding.

**Ticket Detail access**
- BR-40 Ticket Detail is reachable only via a Ticket id/number owned by the current Requester; direct
  navigation to another Requester's Ticket returns a not-found state, never that Ticket's data.

**Transition to Lab 3**
- BR-41 The Development Requester Selector, its client-side stored selection, and the requesterId-as-
  parameter pattern are temporary Lab 2 testing mechanisms. Lab 3 replaces requester identification with
  authenticated session/token identity without changing the underlying Requester data model (see §11).

## 6. UI Specification Summary

Full detail lives in `ui-spec.md`; this is the cross-reference summary.

- **Application shell**: TokTickIT identity, My Tickets / Create Ticket navigation, current-Requester
  identity + Change Requester, active-page indication, responsive (collapsing) navigation.
- **Development Requester Selection**: title, "testing only" explanation, dropdown of active Requesters,
  Continue button, loading/empty/failure states, keyboard accessible.
- **Create Ticket**: system-generated fields visually distinct and grouped near the top; classification
  fields (Category, Related System, Requested Priority) grouped together; Summary/Description given
  generous width; Attachments below the main fields; primary (Submit) and secondary (Cancel) actions at
  the bottom; busy/disabled Submit state; inline validation messages.
- **My Tickets**: search box, filter controls, sort control, pagination, Create Ticket action, desktop table /
  mobile card layout, loading/empty/no-results/failure states.
- **Ticket Detail**: read-only header/classification/description fields, distinct Attachment section
  (list + add control), ownership-blocked state for foreign tickets.
- **Zen Green tokens**: primary `#006B3C`, secondary `#0B7A46`, pale `#EAF6EF`, page background
  `#F5F7F6`, white cards with subtle border/shadow, dark charcoal-green text, distinct editable vs.
  read-only field shading, red validation text/border, amber warning, green success (never color-only).

## 7. Data Changes

New/changed Prisma models (full migration detail owned by Issue 2's branch, summarized here per the
Spec DD requirement to record the design before implementation):

| Model | Key fields | Notes |
|---|---|---|
| `Category` (extend existing) | `id`, `name` (unique), `isActive` (new, default `true`), `createdAt` | Existing Lab 1 model gains `isActive` so "retrieve active Categories" (§8) is meaningful. |
| `RelatedSystem` (new) | `id`, `name` (unique), `isActive` (default `true`), `createdAt` | Same shape as `Category`. |
| `Requester` (new) | `id`, `name`, `email` (unique), `isActive` (default `true`), `createdAt` | The Lab 2 "Development Requester." Kept as a plain domain model (not named `DevRequester`) so Lab 3 can extend it in place with auth fields instead of migrating to a new table — see §11. |
| `Ticket` (new) | `id`, `ticketNumber` (unique, backend-generated), `requesterId` (FK), `categoryId` (FK), `relatedSystemId` (FK), `summary`, `description` (`@db.Text`), `requestedPriority` (enum `LOW\|MEDIUM\|HIGH\|URGENT`), `currentStatus` (enum, only `NEW` reachable in Lab 2), `createdAt`, `updatedAt` | Indexes: `requesterId`, `categoryId`, `relatedSystemId`, `currentStatus`, `createdAt`; unique on `ticketNumber`. |
| `Attachment` (new) | `id`, `ticketId` (FK), `originalFileName`, `storedFileName`, `mimeType`, `fileSizeBytes`, `uploadedAt`, `removedAt` (nullable), `removalReason` (nullable) | Soft removal via `removedAt IS NULL` = active. Index on `ticketId`. |

Relationships: one `Requester` → many `Ticket`; one `Ticket` → many `Attachment`; one `Category` → many
`Ticket`; one `RelatedSystem` → many `Ticket`. All FKs are required (`onDelete: Restrict` — a Requester,
Category, or Related System referenced by a Ticket cannot be hard-deleted; deactivation via `isActive` is
the supported path).

## 8. API Contract

Full detail lives in `api-spec.md`; summary of required endpoints:

| Method & Path | Purpose |
|---|---|
| `GET /api/categories` | Active categories (extends the existing Lab 1 endpoint with an active filter) |
| `GET /api/related-systems` | Active related systems |
| `GET /api/requesters` | Active Development Requesters |
| `POST /api/tickets` | Create a ticket for the selected Requester |
| `GET /api/tickets` | Selected Requester's tickets — search/filter/sort/paginate |
| `GET /api/tickets/:id` | One owned ticket, with its attachments |
| `POST /api/tickets/:id/attachments` | Upload an attachment to an owned ticket |
| `GET /api/tickets/:id/attachments` | Attachment metadata for a ticket |
| `GET /api/attachments/:id/download` | Download an active attachment |
| `DELETE /api/attachments/:id` | Soft-remove an owned attachment |

All Requester-scoped endpoints require a `requesterId` (query parameter for `GET`, body field for
`POST`/`DELETE`) representing the selector's current selection, and enforce ownership server-side per
BR-11–BR-13.

## 9. Acceptance Criteria

**Given (mandatory) examples, kept verbatim:**
- AC-01 Given valid Ticket data, when the Requester submits the form, then one Ticket is saved and the
  official Ticket Number is displayed.
- AC-02 Given no Development Requester is selected, when the user attempts to open My Tickets, then the
  Requester Selection screen is shown.
- AC-03 Given Requester B is selected, when a Ticket belonging to Requester A is requested, then the
  Ticket data is not returned.

**Create Ticket**
- AC-04 Given the form is submitted with a blank Summary, when validation runs, then a
  Summary-required message appears next to the field and no API call is made.
- AC-05 Given a Description shorter than 10 characters, when the Requester attempts to submit, then a
  length-validation message appears and submission is blocked.
- AC-06 Given valid Ticket data and one valid JPG attachment, when the Requester submits, then the Ticket
  and Attachment are both saved and both are visible on Ticket Detail.
- AC-07 Given a 6 MB file is selected as an attachment, when the Requester attempts to add it, then the
  file is rejected with a size-limit message and no upload request is sent.
- AC-08 Given a `.exe` file is selected as an attachment, when the Requester attempts to add it, then the
  file is rejected with an unsupported-type message.
- AC-09 Given a Ticket already has 5 active Attachments, when the Requester attempts to add a 6th, then
  the addition is rejected with a limit-reached message.
- AC-10 Given the backend is unreachable, when the Requester submits a valid form, then a safe failure
  message is shown and all entered field values remain in the form.
- AC-11 Given the Submit button is clicked, when the request is in flight, then it shows a busy state and
  is disabled until the request completes.

**My Tickets**
- AC-12 Given Requester A has 12 tickets and Requester B has 3, when Requester A opens My Tickets, then
  only Requester A's 12 tickets are listed.
- AC-13 Given the Requester searches by a Ticket Number substring, when the search executes, then only
  matching tickets are shown.
- AC-14 Given the Requester filters by Category "Hardware", when the filter is applied, then only
  Hardware tickets are shown.
- AC-15 Given the Requester has zero tickets, when My Tickets loads, then an empty state is shown instead
  of an empty table.
- AC-16 Given the Requester has tickets but the active filters match none, when the list loads, then a
  no-results state with a clear-filters action is shown.
- AC-17 Given more tickets exist than fit one page, when the Requester navigates to page 2, then the next
  set loads and the page indicator updates.
- AC-18 Given the Requester sorts by Requested Priority, when the sort is applied, then the list re-orders
  and the active-sort indicator updates.
- AC-19 Given Requester A is viewing My Tickets, when they switch to Requester B via Change Requester,
  then Requester A's tickets disappear and Requester B's tickets load.

**Ticket Detail & Attachments**
- AC-20 Given a Requester opens Ticket Detail for a ticket they own, when the page loads, then all ticket
  fields render read-only with correct values from the database.
- AC-21 Given a Requester requests Ticket Detail for a ticket owned by another Requester, when the request
  is made, then a not-found/blocked state is shown and no ticket data is rendered.
- AC-22 Given an active Attachment on an owned ticket, when the Requester clicks Download, then the
  original file downloads successfully.
- AC-23 Given a removed Attachment, when the Requester views Ticket Detail, then its metadata is visible
  but Download/Preview is disabled.
- AC-24 Given a removed Attachment, when a download is attempted directly against its API endpoint, then
  the backend rejects the request rather than serving the file.
- AC-25 Given an owned ticket with fewer than 5 active Attachments, when the Requester adds one valid
  Attachment from Ticket Detail, then it appears immediately as active.
- AC-26 Given an active Attachment the Requester owns, when they soft-remove it with a reason, then it
  becomes non-downloadable while its metadata and reason remain visible.

**Requester Selector & accessibility**
- AC-27 Given no active Development Requesters exist, when the Selection screen loads, then an empty
  state is shown and Continue is unavailable.
- AC-28 Given the active-Requesters API call fails, when the Selection screen loads, then a safe failure
  state is shown instead of an unhandled error.
- AC-29 Given the viewport is resized to mobile width (<768px), when any Lab 2 screen is viewed, then no
  horizontal scrolling occurs and all controls remain reachable and touch-friendly.
- AC-30 Given a keyboard-only user, when they tab through the Development Requester Selection screen,
  then all controls are reachable with a visible focus indicator.

## 11. Assumptions and Decisions

- **Ticket Number scheme**: `TK-<year>-<6-digit zero-padded id>` using the ticket's own autoincrement
  `id`. This avoids a separate sequence table or race-prone counting logic — Postgres autoincrement
  already guarantees uniqueness and monotonicity under concurrent inserts. The id is a global sequence
  (not reset per year), which still satisfies BR-01's uniqueness requirement.
- **Ownership failures return 404, not 403**: chosen so that probing a foreign ticket id cannot be used to
  confirm the ticket exists (BR-12, AC-20).
- **`Requester` model name (not `DevRequester`)**: kept generic so Lab 3 can add authentication fields to
  the same table instead of introducing a parallel identity model — the labsheet's example prompt calls
  it a "temporary Lab 2 RequesterUser model," but the underlying entity (a person who submits tickets) is
  permanent; only the *selection mechanism* (BR-41) is temporary.
- **`Category.isActive` added**: Lab 1's `Category` model had no active flag; Lab 2's API contract requires
  "retrieve active Categories," so the field is added now (all four seeded categories default active).
- **Requested Priority enum**: `LOW | MEDIUM | HIGH | URGENT`.
- **Field length limits**: Summary 5–120 chars, Description 10–2000 chars, chosen to be generous enough
  for real descriptions while catching empty/placeholder input.
- **My Tickets pagination**: default page size 10; permitted sizes 10/25/50.
- **Related Systems seed** (≥6 required): Email, Campus Wi-Fi, VPN, LEB2 App, Grade Submission App,
  Printer, Corporate Laptop (7 total, per the labsheet's own example list).
- **Dev Requester seed**: 4 active + 1 inactive, realistic fictional names/emails.
- **Client test directory naming**: the labsheet prints `client/.../lab-02 tests/`; Lab 1 already
  established `client/tests/lab-01/` (no space) as this repo's real convention, so Lab 2 tests live in
  `client/tests/lab-02/` for consistency — file names (`CreateTicket.test.tsx`, etc.) match the labsheet.
- **Duplicate-submission prevention** is UI-only in Lab 2 (BR-22/BR-23); server-side idempotency keys are
  out of scope and listed as a known limitation in `tests.md`.
- **Status enum forward-compatibility**: `currentStatus` is modeled as a full enum (`NEW`, plus values
  reserved for later labs) so Lab 3 doesn't require a breaking schema change, even though Lab 2 only ever
  writes/reads `NEW` (per the explicit scope exclusion in §3).
